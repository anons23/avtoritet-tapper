# Вор в законе — дизайн механики и план реализации

Ветка: `fix/yandex-16plus-stability`

## Концепция

«Вор в законе» должен ощущаться как качественно новая ступень игры, но сохранять привычные тапы.

**Главная схема:** Сходка + тапы + события + NPC-диалоги + телефон + решения + Вес + цепочки событий.

Карточную механику пока не делать отдельной основной системой. При желании карты можно добавить позже как элемент отдельных событий.

## 1. Сходка

На экране постоянно находится сцена сходки:
- стол;
- Вор в законе;
- 3–4 участника;
- предметы на столе;
- телефон;
- фон комнаты/кабинета.

Игрок продолжает тапать по основной интерактивной зоне сцены и получает обычную награду.

Цикл: **ТАПЫ → СОБЫТИЕ → РЕШЕНИЕ → ПОСЛЕДСТВИЕ → ТАПЫ**.

Тапы не убираем: они остаются базовой механикой, поверх которой появляются события.

## 2. Вопрос от участника сходки

Через некоторое количество тапов один из сидящих участников может обратиться к Вору.

1. Участник визуально выделяется.
2. Появляется его изображение.
3. Открывается существующее NPC-диалоговое окно.
4. NPC произносит заранее подготовленную реплику.
5. Игрок получает 2–3 варианта ответа.
6. Игрок выбирает вариант.
7. Система применяет последствия.
8. Диалог закрывается.
9. Игрок возвращается к сходке.

Тематики: проблема внутри зоны, нарушение порядка, вопрос по людям, конфликт, просьба о совете, распределение ресурсов, информация от смотрящего, неожиданная ситуация.

Реплики и варианты ответов хранить отдельно от основной логики, чтобы новые сценарии можно было добавлять без переписывания механики.

## 3. Телефон

Телефон постоянно лежит на столе и является отдельным источником событий.

Разделение:
- **Участник сходки →** внутренний вопрос непосредственно Вору.
- **Телефон →** событие или информация извне.

При звонке:
1. телефон вибрирует/анимируется;
2. экран загорается;
3. появляется имя или тип звонящего;
4. игрок нажимает на телефон;
5. открывается событие или NPC-диалог;
6. игрок принимает решение;
7. применяется последствие.

Возможные звонки: Смотрящий — проблема в зоне; человек из другой зоны — внешний вопрос; посыльный — информация; знакомый — просьба; редкий важный звонок — особое событие.

Телефон должен звонить редко, чтобы оставаться событием, а не постоянным отвлечением.

## 4. Система «Вес»

Добавить отдельный показатель **ВЕС**.

Пример: `ВЕС: 620` или `██████░░░░ 620 / 1000`.

Решения могут увеличивать Вес, уменьшать его, не менять или давать временный эффект.

Примерные значения для прототипа:
- обычное решение: +20;
- хорошее решение: +50;
- важное решение: +100;
- плохое решение: -40.

Значения потом настроить по балансу. Игроку заранее не сообщать «правильный» ответ — последствия должны проявляться после выбора.

## 5. Награды и последствия

Решения могут менять не только Вес:
- +Вес / -Вес;
- +награда / уменьшение награды;
- множитель;
- бонусная серия тапов;
- временный штраф;
- запуск следующего события;
- продолжение сюжетной цепочки.

Не каждое событие должно иметь отрицательный результат.

## 6. Цепочки событий

События желательно связывать.

Пример: Смотрящий на сходке сообщает о проблеме → игрок принимает решение → позже звонит телефон → Смотрящий сообщает об изменении ситуации → позже на сходке появляется продолжение истории.

Рекомендуемые идентификаторы: `eventId`, `chainId`, `step`, `speaker`, `choices`, `effects`.

## 7. Структура данных

Концептуальный пример:

```js
{
  id: "zone_problem_01",
  type: "meeting",
  speaker: "smotryashiy",
  text: "...",
  choices: [
    {
      text: "...",
      effects: { weight: 50, reward: 500 },
      nextEvent: "zone_problem_02"
    },
    {
      text: "...",
      effects: { weight: -20 }
    }
  ]
}
```

Телефонное событие:

```js
{
  id: "phone_call_01",
  type: "phone",
  caller: "smotryashiy",
  text: "...",
  choices: [...]
}
```

Фактические поля адаптировать под существующую архитектуру игры.

## 8. Триггеры

Не привязывать события только к жёсткому количеству тапов. Лучше использовать условия и вероятность.

Учитывать:
- минимальное количество тапов после прошлого события;
- вероятность запуска;
- текущий Вес;
- текущую серию;
- текущую стадию;
- активную цепочку;
- отсутствие открытого диалога;
- отсутствие другого активного телефонного события.

Условный принцип:

```js
if (currentObject === VOR_V_ZAKONE
    && !dialogOpen
    && tapsSinceEvent >= minTaps
    && random() < eventChance) {
  triggerEvent();
}
```

Точные значения подобрать после тестирования.

## 9. Телефон — визуальные состояния

Пользователь может подготовить 3–4 изображения:
1. телефон в покое;
2. экран включён;
3. входящий звонок;
4. активное состояние/уведомление.

При звонке: лёгкая вибрация, свечение экрана, возможно короткий звук и явный визуальный сигнал, что на телефон нужно нажать.

Телефон должен оставаться частью стола, а не превращаться в отдельное полноэкранное меню.

## 10. NPC-диалоги

Использовать существующую систему NPC-диалогов игры, а не создавать вторую независимую систему.

Нужно предусмотреть: изображение говорящего, имя, текст, варианты ответа, эффекты выбора, закрытие диалога и возврат в сцену сходки.

Не допускать конфликтов с существующей системой NPC/modal.

## 11. Визуальная логика

Основной интерактивный объект находится непосредственно в сцене. Не перегружать экран отдельными кнопками.

**сцена → тап по сцене → награда**

**событие → NPC/телефон → решение**

**последствие → возвращение к сцене**

Так сохраняется простота для телефона.

## 12. Что пока не делать

Не добавлять сразу полноценную карточную игру, сложный инвентарь, десятки ресурсов, большое дерево диалогов, слишком частые звонки и постоянные окна поверх сцены.

Сначала сделать небольшой рабочий прототип:
1. Сходка.
2. Обычные тапы.
3. Один NPC-вопрос.
4. 2–3 варианта ответа.
5. Вес.
6. Один телефонный звонок.
7. Один телефонный сценарий.
8. Возврат в основную сцену.

После тестирования расширять систему.

## 13. Порядок разработки

1. **Сцена** — фон сходки и интерактивная область.
2. **Базовые тапы** — сохранить существующее начисление награды.
3. **Вес** — добавить состояние и отображение.
4. **NPC-события** — подключить существующее NPC-окно.
5. **Решения** — добавить варианты ответа и effects.
6. **Телефон** — объект, анимация звонка и обработка тапа.
7. **Телефонные события** — отдельные сценарии внешних звонков.
8. **Цепочки** — связанные события.
9. **Баланс** — частота событий, награды, Вес, последствия.
10. **Полировка** — анимации, звук, вибрация, переходы, мобильная адаптация.

## 14. Главный принцип

Вор в законе не должен ощущаться как «ещё один персонаж, которого нужно тапать».

Игрок всё ещё тапает, но теперь **сидит на сходке, принимает решения, получает звонки, решает вопросы и набирает Вес**.

Именно это должно отличать эту ступень от предыдущих.

Карты можно вернуть позже как редкий элемент отдельных событий, но они не должны заменять основную механику сходки.

## 15. Минимальный первый прототип

- 1 фон сходки;
- 4 участника;
- 1 телефон;
- 1 NPC;
- 3 NPC-сценария;
- 2 телефонных сценария;
- показатель Вес;
- 2–3 варианта ответа;
- несколько типов последствий;
- обычный тап по сходке.

После стабильного прототипа расширять количество персонажей и сценариев.

## Статус

Это дизайн-документ и план реализации. Код игры на основании этого документа пока не менять, пока отдельно не принято решение начать реализацию.
